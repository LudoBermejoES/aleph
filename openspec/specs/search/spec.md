# search Specification

## Purpose

Provide hybrid lexical + semantic full-text search over campaign entities: the existing SQLite FTS5 (BM25-weighted, phrase-capable) keyword path combined with local-embedding-based vector similarity search (via `sqlite-vec`), fused into a single ranked result set. Semantic matching lets queries surface relevant content even when the query and the source text share no keywords — e.g. paraphrased plot descriptions or a character referenced under a different alias — while lexical search remains authoritative for exact name and typo matches. All embedding generation and vector similarity search runs entirely on the local server, with no external API calls and no generative-model (LLM) inference anywhere in the search path, and no answer synthesis: search returns ranked entities and snippets from existing content, never generated natural-language text. Results remain scoped to the requesting campaign and respect existing role-based visibility rules, matching the same access-control guarantees as the prior lexical-only search.

## Requirements

### Requirement: Semantic matching beyond shared keywords

The system SHALL return relevant entities for a query even when the query and the entity's content share no exact keywords, provided the query is conceptually/semantically related to that content, using a locally-run embedding model with no external API calls and no generative-model (LLM) inference.

#### Scenario: Conceptual query surfaces relevant content without shared keywords

- **WHEN** a user searches for "children being corrupted" and a session's summary describes children marked with cult symbols and infected with a supernatural affliction, without using the words "corrupted" or "children" together in that phrasing
- **THEN** that session is returned among the search results

#### Scenario: Alias/identity connections surface across differently-worded content

- **WHEN** an antagonist character has appeared under multiple names across different sessions (e.g. established via aliases or narrative connection), and a user searches using one name
- **THEN** sessions and entities referencing the character under a different name are still ranked among the results if their content is semantically related to the query

---

### Requirement: Hybrid ranking combines lexical and semantic results

The system SHALL combine results from the existing lexical (FTS5) search path and the new semantic (vector similarity) search path into a single ranked result list, rather than replacing one with the other.

#### Scenario: Exact name match still ranks first

- **WHEN** a user searches for the exact name of an existing character (e.g. "Otto Von Grugger")
- **THEN** that character is ranked first in the results, at least as reliably as with lexical-only search today

#### Scenario: Results found only semantically are still included

- **WHEN** an entity is a strong semantic match for the query but shares no keywords with it
- **THEN** that entity appears in the combined result list, ranked according to the fusion of both search paths

#### Scenario: Results found only lexically are still included

- **WHEN** an entity is an exact keyword match but semantically dissimilar embedding-wise (e.g. a short name with little surrounding context)
- **THEN** that entity still appears in the combined result list

---

### Requirement: No answer synthesis

The system SHALL return ranked entities and snippets from existing content, and SHALL NOT generate new natural-language text (no LLM call, no synthesized summary or answer) as part of a search response.

#### Scenario: Search response contains only retrieved content

- **WHEN** any search query is executed, semantic or lexical
- **THEN** the response contains references to existing entities (id, name, snippet drawn from stored content) and does not contain any text that was generated by a language model at query time

---

### Requirement: Embeddings stay consistent with source entity content

The system SHALL generate or update an entity's embedding whenever that entity's searchable content (name, body, or other embedded fields) is created or modified, and SHALL remove an entity's embedding when the entity is deleted.

#### Scenario: Editing an entity updates its semantic searchability

- **WHEN** an entity's body content is substantially edited
- **THEN** subsequent semantic searches reflect the updated content's meaning, not the pre-edit content

#### Scenario: Deleting an entity removes it from semantic search

- **WHEN** an entity is deleted
- **THEN** subsequent semantic searches no longer return that entity, and its stored embedding is removed

#### Scenario: New entities become semantically searchable without manual intervention

- **WHEN** a new entity is created
- **THEN** it becomes findable via semantic search without requiring a manual reindex step

---

### Requirement: Semantic search runs entirely locally

The system SHALL perform embedding generation and vector similarity search entirely on the local server, without calling any external API or third-party service, and without transmitting campaign content off the server for search purposes.

#### Scenario: Search functions without external network access

- **WHEN** the production server has no outbound internet access at query time
- **THEN** semantic search continues to function normally, since the embedding model and vector index are both local

---

### Requirement: Search results remain scoped to campaign and requester permissions

The system SHALL only return semantic (and combined hybrid) search results for entities within the campaign specified in the request, and SHALL respect existing per-campaign role-based visibility rules, matching the same access-control guarantees as the existing lexical search path.

#### Scenario: Semantic results are scoped to the requested campaign

- **WHEN** an authenticated user searches while scoped to Campaign A
- **THEN** no entities belonging to Campaign B are returned via either the lexical or semantic path, even if semantically similar

#### Scenario: Unauthenticated request is rejected

- **WHEN** a search request is made without a valid session cookie or `X-API-Key` header
- **THEN** the system returns an authentication error and no results from either search path

#### Scenario: Visibility-restricted content is excluded for insufficiently privileged requesters

- **WHEN** a semantically-matching entity is marked visible only to DM/co-DM roles, and the requester holds the `player` or `visitor` role
- **THEN** that entity is excluded from the requester's combined search results

---

### Requirement: Acceptable latency on production hardware

The system SHALL return combined hybrid search results within a latency budget suitable for interactive use on the confirmed production hardware (4-core ARM, CPU-only inference), without requiring GPU acceleration or external compute.

#### Scenario: Typical query completes within the latency budget

- **WHEN** a user submits a typical search query against a campaign of realistic size (dozens to low hundreds of entities)
- **THEN** the combined hybrid search response is returned within the documented latency budget (target: sub-200ms added latency for the semantic path beyond existing lexical search timing)
