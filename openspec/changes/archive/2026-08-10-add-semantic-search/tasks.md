## 3. Embedding storage and generation

- [x] 3.1 ~~Add a Drizzle migration creating the `sqlite-vec` `vec0` virtual table~~ **CORRECTION**: not a Drizzle migration, for the same reason section 2's trigram table wasn't — `vec0` is a virtual table backed by a loadable extension, so `CREATE VIRTUAL TABLE ... USING vec0(...)` only parses after `sqliteVec.load(sqlite)` has run on that connection; a plain `.sql` migration file has no way to do that. Added `initVecTable()` in `server/services/embeddings.ts`, called from the same Nitro startup plugin (`server/plugins/watcher.ts`) right after `initFTS5()`. Table: `entity_vectors` (`campaign_id TEXT partition key`, `embedding float[384] distance_metric=cosine`) plus an `entity_vec_map` table mapping `entity_id` (TEXT/UUID) to the integer `rowid` vec0 requires — same two-table pattern as `entities_fts`/`entities_fts_map`.
- [x] 3.2 Implemented `embedText()` in `server/services/embeddings.ts`: lazy-singleton `pipeline('feature-extraction', 'Xenova/multilingual-e5-small', { dtype: 'q8' })`, mean-pooled + normalized, with the `"query: "`/`"passage: "` prefix convention from task 1.4. Input capped at 2000 characters (rough heuristic well under the model's ~512 token window — see code comment; not an exact tokenizer-based cap, accepted as good enough for v1).
- [x] 3.3 Added `scripts/download-embedding-model.mjs` (`npm run download-embedding-model`) which downloads the model into a project-root `models/` directory (not transformers.js's node_modules-relative default, which `npm ci` wipes every deploy). `server/services/embeddings.ts` points `env.cacheDir` at the same `models/` path and sets `env.allowRemoteModels = false` in production, so a missing vendored model fails loudly instead of attempting a runtime network download. Wired into `.github/workflows/deploy.yml`: new "Download embedding model" step before the build, and `models/` copied into the deploy tarball alongside `.output` and migrations.

## 4. Hybrid query and fusion

- [x] 4.1 Implemented in `server/services/embeddings.ts`'s `searchEntitiesSemantic()` (already covered in section 3 above — embed query, KNN scoped by the `campaign_id` partition key). **Correction found here, fixed as part of this task**: a raw `k = N` KNN clause always returns its N nearest neighbors, even for a nonsense/gibberish query with no genuine match — caught by an integration test (`collaboration.test.ts`'s "FTS5 re-index" test) asserting zero results for a random unique term, which failed once the semantic arm was wired into the live endpoint. Added `SEMANTIC_MAX_DISTANCE = 0.15` (cosine distance cutoff) to `searchEntitiesSemantic()`, calibrated empirically against this project's real embedding pipeline (true matches ~0.11-0.16 distance vs. gibberish ~0.18-0.20 — see code comment). Documented as a best-effort heuristic, not a rigorously-calibrated boundary. **Confirmed fragile in practice, not just in theory**: CI (different hardware/ONNX runtime than local dev) failed a borderline true-positive unit test at this exact cutoff, and raising it to 0.17 to fix that fixed nothing — it just broke the gibberish-rejection integration test in the other direction against the real local dev corpus. There is no cutoff with comfortable margin on both sides given this model's actual score distribution; 0.15 is kept only because it's the value that currently passes every known real test case, not because it's confidently correct. Task 5.4's real-corpus spot-check is not optional polish — treat "a weak real match got silently dropped" as the expected failure mode to check for first.
- [x] 4.2 Added `server/services/hybrid-search.ts`: `fuseRankedLists()` (pure RRF, `RRF_K = 60` named constant) and `hybridSearchEntities()`, which runs both arms and fuses them.
- [x] 4.3 Visibility/campaign-scoping is applied once, in `search.get.ts`, to the union of both arms' matched entity ids (post-fusion) — equivalent to applying it identically to each arm, without duplicating the DB-backed visibility-check logic per arm.
- [x] 4.4 Updated `server/api/campaigns/[id]/search.get.ts` to call `hybridSearchEntities()` and return each result's `score` and `arms` (`['lexical']`, `['semantic']`, or both) alongside the existing `name`/`snippet`/`slug`/`type` fields. Semantic arm is gated by a new `runtimeConfig.search.semanticEnabled` flag (`SEARCH_SEMANTIC_ENABLED` env var, default on) — the section 5.3 rollback flag, implemented here since it's a one-line addition once the hybrid path exists.
- [x] 4.5 Added `tests/unit/server/hybrid-search.test.ts` (10 tests: pure-RRF ranking/scoring, exact-name-still-ranks-first, semantic-only match surfaces for a same-meaning-different-words query, nonsense query returns nothing, `semanticEnabled: false` rollback falls back to lexical-only, campaign scoping). Fixed the real bug the first integration run surfaced (4.1's correction) and re-ran the full integration suite (912 tests) green afterward.
