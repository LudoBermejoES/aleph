## Context

Aleph's relation system (`entity_relations` / `relation_types` tables, `server/db/schema/relations.ts`) links rows in the unified `entities` table (`server/db/schema/entities.ts`): one table with `type`, `name`, `slug`, `filePath`, keyed per campaign with a `(campaignId, slug)` unique index. Characters and organizations follow an established "extension table" pattern: `characters.entityId` / `organizations.entityId` are non-null (character) or nullable-but-always-set-on-create (organization) FKs into `entities`, and the create endpoints insert both an `entities` row (`type: 'character'`/`'organization'`) and the extension row in the same request (`server/api/campaigns/[id]/characters/index.post.ts:77`).

Quests (`quests` table in `server/db/schema/sessions.ts`) do not follow this pattern. They have their own `campaignId`, `name`, `slug` columns and are never inserted into `entities`. The CLI's relation resolver (`resolveEntitySlug` in `cli/src/lib/client.js:115`) and the API's relation-create validation (`server/api/campaigns/[id]/relations/index.post.ts:33-36`) both look up exclusively by `entities.slug` / `entities.id`, so a quest slug can never resolve — this is the exact cause of "Error: Entity not found" reported by the user.

Two things complicate the "just mirror characters" instinct:

1. **`quests.entityId` is already taken.** It is an optional pointer _from_ a quest _to_ an existing, unrelated entity (e.g. a quest pointing at an item's wiki page), rendered as "Linked entity: X" on the quest detail page (`app/pages/campaigns/[id]/quests/[slug]/index.vue:86-92`, spec `quest-detail`). This is the same "linked entity" concept `calendars`/`timelines` call `linkedEntityId` — quests are the odd one out in naming. We must not repurpose this column for the entities-mirror FK.
2. **`entity_types` already seeds a `quest` type** (`server/services/entity-types.ts:12`, slug `quest`, icon `flag`) alongside `character`, `location`, `faction`, etc., but nothing ever creates an `entities` row with `type: 'quest'`. This strongly suggests quests were originally meant to be first-class entities and the standalone `quests` table was a later, disconnected addition (it carries quest-specific fields — `status`, `subCampaignId`, `assignedCharacterIdsJson`, `logFilePath` — that don't belong on the generic `entities` row, similar to why characters/organizations have their own extension tables).
3. **Quests also already have a `parentQuestId` self-reference** with full UI support (quest detail "Parent quest" / "Sub-quests" sections, `app/pages/campaigns/[id]/quests/index.vue` tree view, `server/utils/diagram-generator.ts:250-297` quest hierarchy diagrams). This is a single, untyped, quest-only hierarchy edge — orthogonal to the richer relation graph (custom forward/reverse labels, attitude, visibility, cross-type links) the user actually wants to use for "es parte de" / "incluye la sub-misión". It stays as-is; we are not replacing it.

## Goals / Non-Goals

**Goals:**

- A quest slug resolves through the same lookup the rest of the relation system uses (`GET /api/campaigns/:id/entities/:slug`), so `relation create/list/delete` work for quests with zero CLI code changes.
- Quests can be the source or target of a relation with any other entity type (quest-to-quest, quest-to-character as "questgiver", quest-to-location as "takes place in", etc.), not just quest-to-quest.
- Existing quests (including the user's 9 already-created ones) get backfilled so they're immediately relatable without recreating them.
- No behavior change to the existing "linked entity" feature on quests.
- No behavior change to `parentQuestId` / the quest hierarchy tree UI or `diagram-generator.ts`.

**Non-Goals:**

- Deprecating or migrating `parentQuestId` to relations. The two mechanisms will coexist; see Open Questions.
- Changing the entity-graph visualization (`graph.vue`) to render quest nodes. This is a natural follow-on (flagged below) but is not required for CLI/API-level relation support to work, and the graph's node/edge rendering, icon set, and layout heuristics are unaudited for a `quest` node type — better scoped as a separate, focused change once relation usage on quests is validated.
- Renaming `quests.entityId`. See Decision 2.
- Adding CLI flags for `parentQuestId` (`aleph quest create --parent`). Real gap, but a separate, smaller, independent fix — not required to unblock relations and not part of this proposal's Capabilities.

## Decisions

**1. Mirror the _organization_ variant of the "entities row + extension table" pattern: reuse `quests.id` as `entities.id`, rather than adding a new FK column.**
Two such patterns already coexist in this codebase: characters use two distinct UUIDs (`characters.id` != `characters.entityId`, which FKs to `entities.id`), while organizations generate a single UUID and use it as the primary key of _both_ rows (`organizations.id === entities.id`; `organizations.entityId` is a redundant same-value copy of it, `server/services/organizations.ts:60,75,77`). The organization variant is strictly simpler for quests: **no schema migration is needed at all**. Quest creation inserts an `entities` row and a `quests` row that share one `id`. `quests.id` was never a foreign key target elsewhere with a meaning that would conflict, so this is safe.
_Superseded alternative (this doc originally proposed it)_: add a new `quests.graphEntityId` column mirroring the character pattern. Rejected during implementation once the organization precedent was noticed — it would require a schema change, a generated migration, and a two-step NOT-NULL rebuild (Decision as originally written, Migration Plan steps 1–3), all to store a value (`quests.id`) that can just _be_ the shared id instead. Reusing the id is lower-risk (smaller migration surface, matches an existing precedent) and still satisfies the specs, which only require "the quest row stores a reference to that entity's id" — trivially true when the id **is** the reference.
_Alternative also considered and still rejected_: a separate `quest_relations` join table scoped only to quests. Rejected — it would only solve quest-to-quest linking (not quest-to-character/location), duplicate the relation system's schema (labels, attitude, visibility, cascade rules) for no reason, and ignore the pattern the codebase has already standardized on twice.

**2. `quests.entityId` is untouched — it keeps meaning "linked entity" (optional, user-chosen pointer to an unrelated entity).**
Because Decision 1 no longer needs a new column, there is nothing to name and nothing to disambiguate from `entityId`. The existing "Linked entity: X" feature (`app/pages/campaigns/[id]/quests/[slug]/index.vue:231-233`, written by `server/api/campaigns/[id]/quests/index.post.ts:64`) is entirely unaffected: it stays optional, still points at a caller-chosen entity, and has no relationship to the new mirror-entity mechanism.

**3. Enforce campaign-wide slug uniqueness for quests via `ensureUniqueSlug` (already used by characters), instead of the current bare `slugify()` — and use one shared slug for both rows, not two like organizations do.**
Once quests get a row in `entities`, the `entities_campaign_slug` unique index (`campaignId`, `slug`) applies to them too. Quest creation currently does `slugify(body.name)` with no collision check at all (`server/api/campaigns/[id]/quests/index.post.ts`), unlike characters (`ensureUniqueSlug`) — this was also a pre-existing, unrelated gap: two quests in the same campaign could already collide on `quests.slug`, since it has no unique index today. Since `quests.id` now equals `entities.id` for the same row (Decision 1), it is simpler and more consistent to also give them a single shared slug: call `ensureUniqueSlug(db, campaignId, body.name)` once and use its result for both `quests.slug` and `entities.slug`. This both satisfies the stated goal (campaign-wide uniqueness against all entity types) and incidentally fixes the pre-existing quest-to-quest collision gap, with no divergence between "the quest's slug" and "its entity's slug" the way organizations currently have (`entitySlug` vs `orgSlug` in `createOrganizationWithEntity`) — that two-slug split is not needed here and would only be extra complexity.

**4. Backfill preserves each existing quest's own `quests.slug` as-is (URLs must not break), only de-duplicating the _mirror entity's_ slug on collision — the one-shared-slug rule in Decision 3 applies to newly created quests going forward, not retroactively to quests that already have a public slug.**
Backfill for existing quests needs no migration script — a one-time boot-time backfill, following the existing `server/db/backfills/` pattern, does the job.
Since there is no new column to populate, "backfilling" existing quests means only: for every `quests` row with no matching `entities.id`, insert one (`type: 'quest'`, `id` = the quest's own id, `filePath` from `quests.logFilePath`, `visibility` from `isSecret`, `createdAt`/`updatedAt` copied from the quest row, `createdBy` = the campaign's owner, since `quests`/`entities` have no `createdBy` of their own to copy — see resolved Open Question below). This is plain data insertion, not a schema change, so it fits the project's existing boot-time backfill convention (`server/db/backfills/character-images.ts`, `organization-images.ts`, invoked from `server/plugins/migrations.ts`) instead of a hand-written SQL migration — simpler, idempotent by construction (skips quests that already have a mirror row), and consistent with how this codebase already backfills newly-added derived data.

## Risks / Trade-offs

- **[Risk] Slug collision during backfill** — an existing quest's already-assigned slug might collide with an unrelated entity in the same campaign → **Mitigation**: backfill reuses the same collision + timestamp-suffix logic as `ensureUniqueSlug`, so the mirror entity gets a de-duplicated slug (`<slug>-<timestamp36>`); the quest's own `quests.slug` (used for quest URLs, already public) is left untouched, only the mirror entity's slug in `entities` may differ for backfilled rows (see Decision 4). Quests created after this change use one shared slug for both rows (Decision 3), so this divergence only exists for the backfilled cohort.
- **[Risk] Rename/delete must stay in sync between the two rows sharing an id** — `PUT` must also update the mirror entity's `name` (`entities.name`), and `DELETE` must also delete the mirror `entities` row (so `entity_relations` referencing it cascade-delete, per the `onDelete: 'cascade'` FK and `PRAGMA foreign_keys = ON` already set in `server/utils/db.ts`) → **Mitigation**: both endpoints get one additional statement each, mirroring how `characters`' `PUT` already syncs `entities.name` on rename.
- **[Risk] `quests.createdBy` does not exist** (unlike `entities.createdBy` which is `NOT NULL`) → **Resolved**: no new column added; the mirror entity's `createdBy` is set from `event.context.user.id` at creation time (exactly like characters/organizations), and from the owning campaign's own `createdBy` for backfilled rows, since backfill has no per-quest author to copy.
- **[Trade-off] `entities` list/search endpoints (`GET /api/campaigns/:id/entities?type=...`, global search) will start returning quests** once they have rows there, which is desirable for the relation system but is also a visible side effect on any existing "browse all entities" UI/CLI (`entity list`, wiki index) that didn't previously include quests. Not a regression (quests were simply invisible there before) but worth a manual check during implementation that nothing assumes `entities.type` is one of the pre-existing wiki types only.

## Migration Plan

1. Add the new nullable-during-migration FK column to `quests` (Drizzle schema change + generated migration).
2. Data migration step (same migration or a follow-up one, per Drizzle/SQLite migration conventions already used in `server/db/migrations/0033_foamy_makkari.sql` for similar backfills): for every existing quest, insert its mirror `entities` row and set the FK.
3. Make the column NOT NULL once backfilled (if SQLite/Drizzle table-rebuild constraints allow it in one pass; otherwise a follow-up migration, matching the two-step pattern already visible in the `0033_foamy_makkari.sql` migration for `sub_campaigns`).
4. Update `POST /api/campaigns/:id/quests` to insert the mirror entity + use `ensureUniqueSlug` going forward.
5. Rollback: the new column and its mirror `entities` rows can be dropped without touching `quests`' own identity columns (`id`, `slug`, `parentQuestId`, etc.) or any pre-existing relation; low blast radius if reverted.

## Open Questions

- **Exact name for the new FK column** — `graphEntityId`, `selfEntityId`, `linkedGraphEntityId`? Needs a decision before writing the migration; this doc uses `graphEntityId` as a placeholder.
- **`quests.createdBy`** — add it now (bringing quests in line with `entities`/`characters`/`organizations`, all of which require it) or backfill mirror `entities.createdBy` with the campaign owner? The former is more consistent but expands this change's surface into `quest.js` CLI/API request shapes; the latter is more contained.
- **Should `entity list`/global search start surfacing quests now that they have `entities` rows**, or should quest entity rows be filtered out of those endpoints until a deliberate decision is made to expose them there? Leaning towards "let them show up" (least surprising, consistent with every other entity type) but flagging since it's a visible UX change beyond the relation system itself.
- **Should the entity-graph visualization (`graph.vue`/`EntityGraphView.client.vue`) render quest nodes?** Deferred out of this change (see Non-Goals) but the answer affects whether a future change needs new node styling/icon (the `entity_types` seed already has an icon: `flag`) and whether quest-to-quest relations should visually nest the way `parentQuestId` currently does in the quest tree view, or render as flat graph edges like every other relation.
- **Should `parentQuestId` eventually be expressed as a relation** (e.g. a built-in `sub_quest_of` relation type) instead of a bespoke column, now that quests can carry arbitrary relations? Not required by this change — flagging so it's a deliberate decision, not an accident, if a future change proposes removing `parentQuestId`.
- **Should `aleph quest create`/`update` gain a `--parent <slug>` CLI flag** to expose the existing `parentQuestId` (today only settable via the web UI)? A real, adjacent gap the user's workaround attempt also stumbled into, but independent of the relation-resolution fix — worth a follow-up change rather than scope creep here.
